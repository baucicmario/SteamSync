# 09 — UI / MVVM

## UI structure

SteamSync.UI is an Avalonia desktop application using CommunityToolkit.Mvvm.

The important objects are:

- Program
- App
- MainWindow
- MainViewModel
- GameListViewModel
- SettingsViewModel
- GameListView
- SettingsView
- ViewLocator

## MainWindow

MainWindow.axaml is the shell.

It contains:

- sidebar navigation;
- Games navigation button;
- Settings navigation button;
- a ContentControl bound to CurrentPage.

The actual page is therefore supplied by the ViewModel.

## MainViewModel

MainViewModel owns:

- current page;
- GameListViewModel;
- SettingsViewModel.

Its navigation commands simply change CurrentPage.

## GameListViewModel

This is the UI orchestration hotspot.

It owns references to:

- GameDetectionService
- SteamInjectorService
- ArtworkManager
- GameRepository
- UninstalledImageProcessor
- SyncLogger

It exposes observable state such as:

- Games
- IsBusy
- StatusMessage
- SyncProgress
- IsLogPanelVisible
- CurrentSyncPlatform
- sorting state
- IncludeUninstalledGames

CommunityToolkit source generators turn [ObservableProperty] and [RelayCommand] attributes into binding-friendly properties/commands.

## Detect button flow

GameListView.axaml binds the Detect Games button to DetectGamesCommand.

That command eventually runs RunDetectionAsync.

The ViewModel:

1. sets busy/progress state;
2. reads settings;
3. configures detectors;
4. reports detector progress;
5. resolves titles when an API key is available;
6. re-deduplicates after title resolution;
7. upserts to SQLite;
8. reloads the database into the UI.

## Sync button flow

Sync to Steam calls PerformSync(false).

Force Sync calls PerformSync(true).

The ViewModel is responsible for the orchestration, while the actual Steam file manipulation belongs in SteamInjectorService.

## SettingsViewModel

SettingsViewModel reads and writes:

%AppData%\SteamSync\settings.json

It exposes:

- SteamGridDbApiKey
- IncludeUninstalledGames
- launcher detector toggles
- CustomScanDirectories
- NewDirectoryPath
- StatusMessage

It also uses Avalonia's StorageProvider for folder selection.

## Binding architecture

The views bind directly to ViewModel properties/commands.

Example:

<pre>
Button
  Command="{Binding DetectGamesCommand}"
       ↓
GameListViewModel.DetectGamesAsync
</pre>

And game rows bind to DetectedGame properties:

- IsSelected
- Platform
- Title
- IsInstalled
- ArtworkCached
- IsVR
- SteamAppId

## Logging UI

GameListViewModel exposes the SyncLogger.

GameListView binds Logger.LogLines into an ItemsControl.

The logger also writes to a file under AppData.

## UI architecture tradeoff

The ViewModel layer currently contains a lot of orchestration.

That is convenient for a small desktop app, but it means GameListViewModel is a large dependency hub.

If the system grew significantly, separating application/use-case services from UI state would likely improve maintainability. That is a design observation, not a claim about author intent.
